Mobile Roadmap

A prioritised build order for the HotRest companion app — what to ship, in what order, and which parts of the existing Flutter + Supabase codebase each feature reuses rather than rebuilds.

Repo proj_1 Branch dev_v1 Platform Flutter (Android + iOS) Backend Supabase — 76 migrations, RLS live Audience Mobile developer

Start here — who the app is for

This decision shapes everything below

Build a staff operations app. Do not build a guest app.

The product already serves guests well over the web: a guest scans a table QR and lands on /guest-menu/:propertyId/:tableId, or a room QR for /room-service/:propertyId/:roomNumber, with no install step. Asking a guest who is staying two nights to download an app is friction that will lose more orders than it wins.

Staff are the opposite case. A waiter, housekeeper or duty manager is on their feet for an eight-hour shift and cannot carry a laptop. Everything they need — taking an order at the table, flipping a room to clean, checking a guest in at the door — is currently only reachable through a desktop-shaped web panel. That gap is the whole opportunity.

Waiters & kitchen Build — phase 1 Highest daily usage, clearest ROI, order entry at the table.
Front desk & housekeeping Build — phase 2 Check-in at the door; room status updated from the corridor.
Owners & managers Build — phase 3 Read-mostly. Approvals and today's numbers off-site.
Guests Skip — keep QR web Already shipped and install-free. Revisit only as a PWA prompt.

What the backend already gives you

Reuse, don't rebuild

Nearly all business logic already lives in platform-agnostic service classes that talk to Supabase directly. The mobile app should import these unchanged and build only new UI. The screens are the throwaway part; the services are not.

Ready to call as-is

  • Order lifecycle — create, append, discount, split-pay, settle, refund, cancel restaurant_service.dart · 958 lines
  • Check-in / check-out, rooms, reservations, guests, expenses booking_service.dart
  • Clock-in / clock-out with an open-record lookup shift_service.dart · clockIn, clockOut, getMyActiveRecord
  • Notification feed with a live stream notification_service.dart · watchNotifications()
  • Org, property list and membership resolution organization_service.dart · get_my_properties()
  • Invoices, menu PDFs, PayHere payments invoice_service · menu_pdf_service · payhere_service

Already enforced server-side

  • Row-level security on every tenant table — the app inherits it with no extra work
  • Roles: owner / manager / staff, plus a per-section privilege map of none / view / edit
  • Thirteen permission sections, keyed and already named hotel_dashboard … restaurant_cancellations
  • Plan limits — max properties, users, rooms, tables; trials and subscription state
  • Soft delete, rate locking, booking-channel attribution, menu modifiers

Live realtime today

  • Kitchen order stream with audio alerting kitchen_screen.dart · channel('kitchen_orders_rt')
  • Table floor order changes table_floor_screen.dart
  • Notifications and the guest menu feed
  • Gap: only restaurant_orders is in the realtime publication. Bookings, rooms and check_ins need adding for phase 2.

Notes for the developer

Read before estimating
01

Share the services, fork the screens

Everything under lib/services/ is plain Dart against Supabase with no widget dependencies — import it directly and it will work. The web screens are the opposite: restaurant_management_screen.dart is 3,538 lines and pos_screen.dart is 3,014, both built around wide layouts and hover. Rebuild the UI under lib/presentation/mobile/. Any business rule you find yourself reimplementing is a signal it belongs in a service instead.

02

The existing mobile folder is not a starting point

lib/mobile/ holds a five-screen guest self check-in flow on the old Navigator plus HotelSession pattern, predating GoRouter and Riverpod. Decide early whether to retire it or port it; leaving it in place while building a second mobile app on the newer pattern will confuse everyone who joins the project.

03

Extend the realtime publication before phase 2

Only restaurant_orders is published for realtime. The arrivals board and room status screens need bookings, check_ins and rooms added too, or they will fall back to polling and drain battery. One migration.

04

Push needs a server-side trigger, not just a client

Notification rows are written by the app today and read back over a stream. Real push means an edge function on insert that resolves the target device tokens and calls FCM. Budget for a device-token table and the token refresh lifecycle — it is the part that usually overruns.

05

Security is already handled — do not re-implement it

Tenancy is enforced by row-level security, hardened across several migrations. The app signs in with the same anon key and a user JWT, and sees only its own property's rows. Never add a service-role key to a mobile binary; anything needing elevated rights must go through an existing RPC.

06

Two device classes, not one

Order entry, housekeeping and clock-in are phone features. The kitchen display and shift rota are tablet features and will not compress to 400px honestly. Agree the target devices before layout work starts, and keep the kitchen screen landscape-locked with the wake lock held.

07

Keep subscription purchase out of the app

PayHere is wired up on web. Selling or upgrading a plan inside the binary pulls both stores' in-app purchase rules into scope. Show plan state and limits read-only, and send upgrades to the web checkout.

Deliberately not building

Written down so it is a decision, not an oversight
A guest-facing app The QR web flows already cover menu, room service and check-in with no install. Revisit only as an install prompt on the existing web pages.
Superadmin on mobile Internal tooling used by a handful of people who all have laptops. No case for the build cost.
In-app plan purchase Triggers store in-app purchase rules and their commission. Keep checkout on web and link out.
Full desktop parity Menu engineering, ingredient costing and property configuration are desk work. Leave them on web permanently.
Channel manager sync Booking channels are recorded as attribution only. Live OTA sync is a backend product decision, not a mobile one.

Decisions needed before phase 0 starts

How deep does offline have to go? Blocks F-05 Read-only cache is a fraction of the cost of a full write queue. Taking orders with no signal is the expensive version — worth it only if venues actually have dead zones.
iOS and Android together, or Android first? Blocks F-01 Android-first cuts release overhead and store review from the pilot. Flutter makes the second platform cheap later, but the App Store account and device testing are not free.
Which receipt printers must be supported? Blocks R-06 Named models let this be a three-day task. "Whatever the customer owns" turns it into an open-ended compatibility exercise.
Is verified clock-in wanted, and by what method? Blocks M-02 Location adds a permission prompt and a privacy conversation. A premises QR achieves most of the same control with neither.
Retire or port the existing guest check-in flow? Blocks F-01 It currently owns the mobile entry point, so something has to happen to it in the first ticket either way.
